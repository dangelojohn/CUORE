All adapter contact goes through the running CUORE server (`http://127.0.0.1:5000`, no token configured). The runner is `run_scan_2026-10-22.py` (same folder). It was not executed.

Run (only when the car is ready):

## State dir and scan id

- `state_dir` = `C:\ProgramData\cuore` (confirmed from the server's own audit path; `CUORE_STATE_DIR` is unset, `%PROGRAMDATA%\cuore` wins). Files that matter:
  - `observations.jsonl` (every from-car read; kinds below)
  - `audit.jsonl` (every session open/close, route, errors; also records any `hard_reset`)
  - `addresses.json` (confirmed module addresses, currently ABS only)
  - `exports\*.cuore.zip` (AlfaCore bundles)
- Scan id convention (`cuore/live/scanlog.py`): `SCAN_<yymmddHHMM>` of the FIRST from-car observation in a cluster. Consecutive observations less than 15 minutes apart are one scan. So the legislated block, the UDS block and the DID reads form one scan only if no gap exceeds 15 minutes. The VIN on the scan comes from the first observation that carries one; `A3` (Mode 09 VIN) sets the link VIN first so later observations are tagged.
- Export afterwards (reads only): `GET /api/scans/ZASFAKPN5J7B88115` (list), `GET /api/scans/ZASFAKPN5J7B88115/<scan_id>/export?fmt=json` (the runner fetches these in C4/C5). AlfaCore bundle is a separate, later, human step: `POST /api/export/scan/<scan_id>?vin=ZASFAKPN5J7B88115` (writes only a zip under `exports\`).

## Order (legislated first, UDS second, no legislated read after UDS)

The 2026-10-19 NO DATA happened on legislated reads that followed UDS sessions. `ops._legislated_routes_in_order` already prefers the route that `verify_bus` proved (`probe_stn_protocol`), then 29-bit (STP 34), then 11-bit (STP 33), and `_obd_read` retries once on the other route by itself. Record the order that was actually run: the runner writes it to `manifest.json` (`order`, `legislated_done_at`, `legislated_route`).

## If a read returns NO DATA (or any warning/error)

1. Save it. The runner always writes the raw response and lists it under `issues` in `manifest.json`.
2. Legislated reads (Phase A): no extra retry from the runner. `ops._obd_read` has already tried the other route once (`route_fallback` appears in the response). That is the one retry.
3. UDS reads (Phase B): one retry after 3 seconds, same session type, nothing else. Then move on.
4. Do NOT reset the adapter. The only reset path is `CUORE_RESET_BEFORE_LEGISLATED=1` in the CUORE server's environment (it makes `Session.untarget()` call `hard_reset()`, ATWS, once per session). It is off by default and `start-cuore.ps1` does not set it. Leave it unset tonight unless you decide otherwise before starting. Also leave `CUORE_ADAPTER_BAUD` and `CUORE_PASS_FILTER_PROBE` unset.
5. If Phase A step A2 fails to verify, the runner aborts before sending anything else. If all of Phase A is NO DATA, do not fall through to "fixing" it with UDS sessions; stop and read `audit.jsonl`.
6. Never re-run a legislated step after Phase B has started. A legislated NO DATA after UDS is the known 2026-10-19 pattern, not a new finding.

## Items with no read-only path in CUORE (stated, not invented)

- UDS `19 0A` (reportSupportedDTC): no function sends it. `19 02` with mask `FF` (B1) already returns every tracked code with its status byte, so the codes are covered. `19 01`, `19 04`, `19 06` exist (`dtc_detail.py`) and are used in B4.
- Radio / nav (ETM 0x6F): registered on CAN-IHS. With cable `none` CUORE has no route to CAN-IHS (2026-10-19 coverage: "needs blue A5 cable").
- ParkView camera / PAM: PAM is registered on CAN-CH, address unknown, route needs the grey A6 cable. No identity read for a camera exists in CUORE. The only chance on CAN-C is the optional full sweep B8, and silence there does not mean the module is absent.
- DTCM, ESM, DASM: no confirmed address for this VIN (`addresses.json` has ABS only). `/module/{code}/dtcs|identity` returns 400 for them. Only `discover` can find them, and the HTTP `discover` probes F190 only (the Python `ops.discover(probe_dids=[...])` option for modules that refuse F190 is not exposed over HTTP).
- Mode 09 beyond the VIN (calibration IDs, CVN, IUPR): the reader exists only inside fullscan (forbidden below).
- Store kind `module_identity` is written only by `ops.sweep_bus_full` (fullscan). The HTTP identity route records kind `identity`.
- Hypothesis 8c659dfc inputs (item 6): ambient vs IAT vs fuel level come from A8 (Mode 02), A9 (PID 46, 0F, 2F, 05) and B5 (ECM DID 1001, 1956). There is no ECM DID for external air temperature in the catalogue; PID 46 is the source.
- Prior ECM EVAP state for reference (observation 2026-10-19 00:30): P0455 and P0456 status 0x4D, P0440 status 0xCD, 121 codes tracked, most at 0x40.

## Notes on side effects that are not car writes

- `observations.jsonl` and `audit.jsonl` grow; `addresses.json` may gain a DTCM row if B7 matches.
- Every HTTP call opens and closes COM3 once (`~1.3 to 5 s` each). The whole plan is roughly 50 to 60 sessions without B8, so budget about 4 to 6 minutes; keep the charger on.
- The first transmit session on an unverified bus would auto-verify anyway; A2 does it explicitly so the legislated route is fixed before any other read.

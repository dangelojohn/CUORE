# Methods and gotchas

- Tests: plain scripts `cuore/tests/check_*.py`, `mes-log-mcp/tests/check_*.py`, `obd2-mcp/tests/check_*.py`; each sets CUORE_STATE_DIR to a temp dir before importing cuore and never writes to C:\ProgramData\cuore. Run them all once before a commit: `for t in ...; do .venv/Scripts/python.exe $t; done`.
- Headless Edge on this PC: `--dump-dom` and `--screenshot` do not work; drive Edge over the DevTools Protocol (pattern in `cuore/tests/check_live_widgets.py`) and kill it by its temp `--user-data-dir` with `cuore/tests/_edge_cleanup.py`, otherwise processes leak (266 found once).
- Verifying links: YouTube via oEmbed; forums and part sites block plain HTTP (202 bot wall or 403), so verify by opening the page in headless Edge and reading the title and first post, or the product image's natural size.
- Jinja: a dict key named `items` is shadowed by `dict.items()`; use bracket access or rename. Each `*_routes.py` module creates its own Jinja environment, so Jinja globals must be registered on each (see `experience_globals.py`, `timeline_routes.py`).
- Starlette uploads arrive as `starlette.datastructures.UploadFile`, not FastAPI's subclass; duck-type on `filename`/`read`.
- CUORE health endpoint: `/api/health`. The keep-alive identifies cuore by the health body. `cmd /c` needs extra outer quotes.
- Owner's manual (2018 US Stelvio, Mopar PDF) is a CONFIRMED source; decode the maintenance plan's bullet columns by character x-position.
- MES language files hold only description fragments; the code-to-text map is in MES's encrypted database (left alone).
- Git: agent-driven `git push` is blocked by the permission classifier; the owner approves a direct `git push github main`. Remote `forge` is unrelated; never push there.
- PDF sheets: reportlab in the project venv; render with pypdfium2 and look at the PNG; one US Letter page each; generators live in `docs/vehicles/<VIN>/pdf-sources/`.
- Serving "Tell CUORE" (`/m/{vin}`) to a phone on the shop LAN: the bind setting is `CUORE_HOST` (`cuore/config.py`, default `127.0.0.1`), not a separate `CUORE_BIND` -- one setting already does this, so a second was not added. Setting `CUORE_HOST=0.0.0.0` in the keep-alive makes the app reachable from every device on the LAN with **no authentication** unless `CUORE_TOKEN` is also set -- that is the owner's decision, not a default (see `Settings.lan_exposed`/`unguarded_lan`). `GET /m/{vin}/qr` only renders the LAN URL when `lan_exposed` is true; it prints the URL as selectable text (no `qrcode` package in this venv, and a from-scratch QR matrix generator was out of scope) rather than a QR image.
- **Three live-layer findings from the first real bench session (2026-10-13, vLinker FS r2 / STN1170 v4.3.2), all fixed in `cuore/live/`:**
  1. *Gateway-silent CAN-C needs an active probe.* This car's Security Gateway Module means CAN-C carries no broadcast traffic, so passive listening alone reads as a dead bus. `cuore/live/ops.py:verify_bus` now falls back to an active Mode 01 PID 00 probe (`_active_probe_0100`) before giving up, and marks the bus `verified_by="active_probe_0100"` so later reads know to use the route the probe actually got an answer on.
  2. *This car answers legislated OBD only on the 29-bit route.* `18DB33F1 -> 18DAF110` (ECM) / `18DAF118` (TCM), not the 11-bit `7DF`/`7E8` pair -- the opposite of what an earlier (2026-09-25) note on this same car assumed. `cuore/live/ops.py:_obd_route` now prefers whichever STP protocol the active probe was verified against; `cuore/live/transport.py` (session open, ~line 144) restates the 29-bit functional header via `ATCP18`/`ATSHDB33F1`/`ATSTFF` (a single 8-digit `ATSH` is silently ignored by this firmware and leaves the old header in force -- reads as NO DATA, not an error).
  3. *`STFAC` on this STN firmware wipes the default pass filters.* After `STFAC` (used when adding custom pass filters, `cuore/live/capture.py:_add_filters`), every reply reads NO DATA because the firmware's default filters are gone too, not just overridden. Fix (`cuore/live/transport.py`, same session-open path, right after the STFAC path runs): re-issue `STCFCPC` + `STP <protocol>` to restore the defaults, then restate the functional header again -- `STP` resets it as well.
- **An MCP server process holds the code it started with.** `obd2-mcp/server.py` and `mes-log-mcp/server.py` run as long-lived subprocesses under Claude Code's MCP connection; editing either file does not change what the running tools do until the connection is torn down and rebuilt with the `/mcp` command (reload/reconnect). A code fix that "doesn't seem to take" after an edit is usually this, not a real regression -- reload before re-diagnosing.
- `cuore/services/cache.py:get_or_build(key, build)` is a small in-process memo cache (16 entries, LRU) keyed on whatever makes the value stale -- never just the VIN. The shared convention across bridges: `("workup", vin, mes_bridge.newest_mtime(vin))` for anything built from the MES log corpus (used by `bench_routes.py`, `flow_bridge.py`, `tests_bridge.py`, `timeline_bridge.py`, `dossier_bridge.py`, `jobs_bridge.py` and others -- this is what took the Report page from 30 s to 5 s and the Job page from 3.2 s to 0.3 s, 2026-10-13); `("scan_health", vin, scan_id, observations.jsonl's mtime)` for the scan health report (`scan_health_bridge.py:build_cached`); `("bench_tree_candidates", vin, codes, mtime)` for the Bench fault-tree view. A new or edited log/observation moves the mtime key component and the stale entry simply falls out -- no invalidation hook needed, but a cache key that forgets to include the right mtime will silently serve a stale page.
- Tell CUORE's phone URL moves with the PC's LAN address: cuore binds `CUORE_HOST=0.0.0.0` (set in the launchers) and the shop PC is on DHCP, so the IP in the `/m/{vin}/qr` URL (192.168.68.80 as of 2026-10-13; was 192.168.0.161) can change on a reboot or router restart -- check the current address before handing a phone the link, don't assume last session's. The Windows Firewall rule for inbound TCP 5000 needs an admin to run once (`New-NetFirewallRule -DisplayName "CUORE 5000" -Direction Inbound -Action Allow -Protocol TCP -LocalPort 5000 -Profile Any`); without it the LAN bind is correct but nothing outside the PC itself can reach the port.
- "Read this photo" (`POST /api/vision/{vin}/read`, `cuore/services/vision_bridge.py` + `cuore/api/vision.py`): a value read from a photo is a **suggestion the human confirms**, never a car measurement -- when the confirmed value is saved as an owner event, the caller stamps `fields_meta[key] = "photo"` on that field (same provenance convention `cuore.live.owner_events` already uses) so the record still says it came from a picture, not an instrument. Field names in the response are the real `cuore.live.owner_events.TAXONOMY` field names for the hints that map onto one kind (`fuel_pump` -> `fuel/fill_up`, `oil_bottle` -> `fluids/engine_oil_change`, `part_label` -> `parts_repairs_elsewhere/part_fitted_elsewhere`, `receipt` -> `fuel/fill_up`); `odometer` returns `odometer_km` with `suggested_kind: null` because that is the event's own top-level field, not a kind field. Provider is `CUORE_VISION_PROVIDER` (default `none`, which is deliberately the honest "not set up, fill in by hand" answer -- CUORE runs offline by rule, so a vision backend is never silently on). `claude` only turns on with `CUORE_VISION_PROVIDER=claude` **and** `ANTHROPIC_API_KEY` set -- that call leaves the LAN and goes to Anthropic over plain HTTPS via `urllib` (no `anthropic` SDK in this venv, and none was added), so it is the owner's explicit, informed choice, never a default. `tesseract` is a probe-only stub (`_find_tesseract` checks PATH and `C:\Program Files\Tesseract-OCR\tesseract.exe`); nothing is installed there today and no OCR is wired up behind it. Tests (`cuore/tests/check_vision.py`) monkeypatch `cuore.services.vision_bridge.urllib.request.urlopen` to return a canned Messages-API body rather than calling the real network.
- **Durable archive (2026-10-14):** `scripts/backup-cuore-state.ps1` is the incremental, append-only, sha256-dedup backup for both `C:\ProgramData\cuore` (-> `docs/vehicles/<VIN>/state-backup/<date>/`) and Claude Code session data -- transcripts, every `tasks\*.output` agent transcript, and scratchpad screenshots/html/json (-> `docs/sessions/raw/<date>/<session-id>/`), regenerating `docs/sessions/<date>-agent-discoveries.md` for any session with new agent output; `scripts/save-session-artifacts.ps1` does the same for one named session id. Nothing already written is ever deleted or overwritten -- a file whose sha256 matches its last capture is just marked `skipped-unchanged`, not recopied. Secrets (`sk-ant-*`, `AKIA*`, `"password": "..."`) are redacted wherever text is copied or digested, even inside a gzipped (>5MB) file -- see `scripts/_backup-common.ps1`. `scripts/hooks/pre-push` is the versioned source for a git `pre-push` hook that runs this archive before every push; **it is not installed** (an automated installer for it was refused by the permission classifier as unauthorized persistence) -- the owner installs it by hand, once per clone: `Copy-Item scripts\hooks\pre-push .git\hooks\pre-push`. Because git fixes the set of commits a push will send *before* `pre-push` runs, a commit the hook makes is never part of that same push -- by design the hook aborts (exit 1) and asks for a plain `git push github main` re-run to pick it up; the archive step's own failures never block a push (logged to `docs/sessions/archive-errors.log`, hook exits 0).
